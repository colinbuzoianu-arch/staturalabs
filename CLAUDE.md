## Core data model principle
Tenant hierarchy: `company` → `site` (aka "workplace") → `workstation` → `task` → `posture_sample` → `body_region_score`, plus `manual_input` (weights/forces) and `assessment_session`. No `employee_id` or anything that could hold one, anywhere near the workstation/task/posture chain. See ERGO_COMPLIANCE_BY_DESIGN.md §3.1 and "Tenant & role hierarchy" for the full rationale.

`AssessmentSession.mode` (`AssessmentMode`: `SCHEDULED` | `CONTINUOUS`, `@default(SCHEDULED)`, `NOT NULL`) records which capture regime produced a session — never inferred, never left to a default at read time (ERGO_COMPLIANCE_BY_DESIGN.md §3.11). `CONTINUOUS` exists as a schema value only: there is no implementation behind it anywhere in the app. `createAssessmentSession()` (`src/lib/assessment-session.ts`) is the single gate for creating a session and throws a clear "not yet implemented" error if asked for `mode: CONTINUOUS` — every future session-creation code path is expected to go through this function rather than calling `prisma.assessmentSession.create` directly, so that gate can't be silently bypassed. Existing rows predating this column were backfilled to `SCHEDULED` explicitly in the migration that added it (`prisma/migrations/20260716063952_add_assessment_session_mode`), not left to ride on the column default — see that migration's comments and the "known gotchas" note below on hand-written migrations.

`AssessmentSession.pilotContext` (nullable `String`, `prisma/migrations/20260716095235_add_assessment_session_pilot_context`) is free-text, internal-only audit-trail metadata (§3.6) — an admin's note on what a session was actually for (e.g. a technical pilot at a partner site, an internal validation study), so pilot/test data can be told apart from real customer data later. Deliberately not surfaced anywhere in the customer-facing dashboard (`src/app/(app)/**`) — set and viewed only via `/admin/workstations/[workstationId]/sessions`, the first real UI on top of `createAssessmentSession()`. A separate migration from `mode` even though both categorize "what kind of session this was": the `mode` migration was already applied before `pilotContext` was requested, so combining them would have meant reverting an applied migration rather than just adding a new one.

Human accounts (distinct from the data model above): `super_admin` (founder, cross-company), `l3_support` (escalation tier, reserved, currently founder), `company_admin` (scoped to whole company, all sites), `site_admin` (scoped to one or more sites via a `site_assignment` join table, not the whole company). Escalation flow: site_admin → company_admin → l3_support → super_admin. All are invite-provisioned — no public sign-up. Company/site admins are real people with names/emails; workstations never are.

**Schema built (M2 of `SLD_IMPLEMENTATION_PLAN_demo-loop.md`): a process/risk/action register sitting alongside the assessment chain above.** Full design/rationale lives in that plan doc — read it before touching any of this. `Site` → `OrgUnit` (self-referencing tree — `PLANT`/`DEPARTMENT`/`AREA`/`LINE`, `siteId` denormalised on every node) → `Workstation` (`orgUnitId` nullable, additive only — `Workstation.siteId` and every `require*Access` wrapper stay unchanged, the org tree is never load-bearing for authorization) and `Process` (an ordered set of `Task`s via `ProcessTask`, no separate `ProcessStep` entity — `Task` already means "a specific job at a workstation"), then `RiskAssessment` (of a workstation *or* a process, exactly one, hand-added CHECK `RiskAssessment_exactly_one_subject_check`) → `RiskFinding` (against a `Hazard` from a versioned catalog) → `ExposureMeasurement` (instrument/survey readings vs. a legal limit — deliberately not merged with `ManualInput` despite the similar shape: different lifecycle and consumer) and `Action` (from a `RiskFinding` or an `AssessmentSession`, exactly one, hand-added CHECK `Action_exactly_one_source_check`; `ActionStatusEvent` append-only history). `RiskFinding`/`RiskAssessment` reuse the existing `RiskBand` enum rather than inventing a second scale, so ergonomic scores and risk findings speak one vocabulary. `RiskMatrixVersion`/`RiskMatrixCell` follow the exact `MethodologyVersion` fail-closed, single-active-version pattern (ERGO_COMPLIANCE_BY_DESIGN.md §3.14), including a hand-added partial unique index (`RiskMatrixVersion_isActive_unique_when_true`) — `lookupRiskMatrixCell()` (mirroring `lookupScoringRule()`) is still **to build**, per M3. `Action.responsibleUserId` references `PlatformUser` only (a plain `@db.Uuid` column, not a DB-level FK); a role, never a worker identity, goes in `responsibleRoleLabel` (§3.13).

Landed as five hand-written migrations, `prisma/migrations/20260730120000_add_process_risk_action_enums` through `20260730120400_add_actions` (enums-only migration first, per the gotcha below), applied via `prisma migrate deploy` and re-verified live: all 24 tables have RLS enabled, both new CHECK constraints and both partial unique indexes confirmed present, and both CHECK constraints proven to actually reject bad inserts at the DB level (not just the app layer). Seeded: a 15-row system hazard catalog (`Hazard`, `companyId IS NULL`, `isSystem = true`) covering all 13 `HazardCategory` values, and `v1-generic-5x5` (`RiskMatrixVersion`, active) with all 25 `RiskMatrixCell` rows (`riskScore = probability × severity`, banded `LOW ≤4 / MODERATE 5–9 / ELEVATED 10–14 / HIGH ≥15`) — no INCDPM/Darabont-shaped matrix seeded, per ERGO_COMPLIANCE_BY_DESIGN.md §3.7/§5.

**M3 lib gates built** (`SLD_IMPLEMENTATION_PLAN_demo-loop.md` M3) — one creation/transition function per rule, following the `createAssessmentSession()` pattern: `createOrgUnit` (`src/lib/org-unit.ts`, enforces `parent.siteId === siteId` and walks the parent chain checking for cycles and `MAX_ORG_UNIT_DEPTH`, both against a pure `validateOrgUnitParent` core unit-tested directly against an in-memory graph — same pure/impure split as `matchScoringRule`/`lookupScoringRule`); `createProcess`/`addTaskToProcess` (`src/lib/process.ts`, the latter enforcing `task.workstation.siteId === process.siteId` — the check that stops a process reaching across sites); `matchRiskMatrixCell`/`lookupRiskMatrixCell` (`src/lib/risk/matrix-lookup.ts`, a direct mirror of `matchScoringRule`/`lookupScoringRule`: `null` on no match, throws on an ambiguous match) plus `getActiveRiskMatrixVersion` (`src/lib/risk/matrix-version.ts`, mirrors `getActiveMethodologyVersion` — fail-closed on zero active rows); `createRiskAssessment` (`src/lib/risk/risk-assessment.ts`, `validateExactlyOneSubject` pure-checks the workstation-xor-process rule before ever reaching the DB CHECK, and `matrixVersion` is never accepted as input — always resolved via `getActiveRiskMatrixVersion`); `transitionAction` (`src/lib/action.ts`, `ACTION_STATUS_TRANSITIONS` is the legal-transition table — `VERIFIED`/`CANCELLED` terminal, reverts allowed `IN_PROGRESS → OPEN` and `IMPLEMENTED → IN_PROGRESS` — `validateActionTransition` additionally requires a `verificationOutcome` plus either a `verificationAssessmentId` or a non-blank `verificationNote` override before allowing `→ VERIFIED`; updates `Action` and writes the append-only `ActionStatusEvent` row in one `prisma.$transaction`). 46 new Vitest cases across 5 test files (124 total, all green), `tsc --noEmit` and `biome check` both clean. Nothing calls `prisma.X.create`/`prisma.action.update` directly for any of these six operations anywhere in the app yet — these functions exist but have no caller until the write surface below is built.

**M6 analysis views built** (`SLD_IMPLEMENTATION_PLAN_demo-loop.md` M6, demo steps 6 and 10) — two read-only pages, deliberately not a BI layer. `(app)/workstations/[workstationId]/risk` (linked from the existing workstation page): the latest `APPROVED` `RiskAssessment`'s findings across every `HazardCategory` (not just ergonomic) with `ExposureMeasurement`s flagged when over their `limitValue`, ergonomic scores reusing `buildRegionResults()` (the most recent `PostureSample` per task, summarized as a concerning-region count rather than the full per-region table the task page already shows — that detail is one click away, not duplicated), open actions scoped to the workstation via either `riskFinding.riskAssessment.workstationId` or `assessmentSession.workstationId`, and a risk-band trend across every assessment regardless of status. `(app)/sites/[siteId]/risk-overview` (linked from the existing site page): workstations ranked by their latest approved assessment's worst band, findings aggregated by hazard category site-wide, and three action tables (open / overdue / awaiting verification, the last being `status === IMPLEMENTED`). `worstRiskBand()`/`riskBandRank()` (`src/lib/risk/band-severity.ts`, unit-tested) rank `RiskBand` for display/sorting only — this ranking never feeds a scoring or matrix-lookup decision. ## Scoring methodology
Independently designed, inspired by public standards (ISO 11228, EN 1005) — not a reimplementation of any licensed/trademarked methodology. Scoring rules live as versioned rows in the `ScoringRule` table (methodology `v1-2026-07` seeded), not hardcoded logic, so thresholds can change without redeploying and past sessions can be re-scored under a new rule version. Angles are stored and compared in **flexion-from-neutral convention** (0° = upright/neutral, increasing = more flexed) — any future angle-capture code must convert raw pose-landmark angles to this convention before a rule lookup; do not add a second convention. `ELBOW_LEFT`/`ELBOW_RIGHT` and `NECK` are the `BodyRegion` values with a non-monotonic rule set (ELBOW: `HIGH` below 20°, `LOW` 20–100°, `HIGH` above 100°; NECK: `HIGH`/`ELEVATED`/`MODERATE` below 0° for backward extension, `LOW`/`MODERATE`/`HIGH` above 0° for forward flexion, with the two `HIGH` bands carrying different `riskScore`s — 3 forward, 4 backward) — the lookup must do a real per-row range check, not a threshold cascade, or these will silently score wrong.

Which `ScoringRule` version is "current" is itself data, not a code constant: `MethodologyVersion` (`version`, `isActive`, `activatedAt`) tracks it, with a partial unique index enforcing at most one active row at the DB level. `getActiveMethodologyVersion()` (`src/lib/scoring/methodology-version.ts`) is the only place that reads it — zero active rows is a misconfiguration and fails closed (throws), never silently falls back to a constant or "the latest by sort order."

**Known limitations of v1, not yet solved:**
- No holding-time/duration dimension — v1 scores an instant posture, not a sustained one. ISO 11226 ties allowable holding time to angle (steeper posture = shorter allowable duration); this is a separate design task, not folded into `ScoringRule` yet.
- `ELBOW_LEFT`/`ELBOW_RIGHT` are gated to `CameraAngle.SAGITTAL`, which assumes the reaching motion happens in front of the body (the common case in assembly-type work). Invalid for tasks involving lateral/side reaching with a bent elbow — the elbow's effective movement plane rotates with the upper arm's orientation, unlike TRUNK/NECK/KNEE whose flexion plane is fixed by the joint's own anatomy.
- `SHOULDER_LEFT`/`SHOULDER_RIGHT` have **no camera angle gate, deliberately, and this isn't a TODO to fill in** — it's a real single-2D-camera measurement limitation. The formula measures arm-elevation magnitude without direction (matching how RULA/REBA-style tools generally score upper-arm posture), but a sagittal camera foreshortens lateral abduction and a frontal camera foreshortens forward flexion — no single required angle makes this measurement reliable for an unconstrained task. Concrete driver for §5's still-open 2D-vs-stereo decision, not a gap to patch with a guessed gate.
- `WRIST` has no `BodyRegion` values or rules yet — true wrist deviation needs MediaPipe Hand Landmarker (Pose Landmarker's single wrist point isn't enough), a capability decision still pending.
- **Monocular far-side-limb occlusion is a real, permanent limitation of single-SAGITTAL-camera capture, not a `MIN_LANDMARK_VISIBILITY` tuning problem — confirmed against a live capture, not just reasoned about.** In a genuine side-on view, the far side's ELBOW/KNEE/ANKLE are partially hidden behind the subject's own torso; MediaPipe correctly reports low visibility for them (observed: leftElbow 0.44, leftKnee 0.27, leftAnkle 0.44, vs. 0.84–0.998 for the same joints on the near side, shoulders/hips near 1.0 on both sides). No visibility threshold fixes this — it's not noise, it's a joint the camera structurally can't see well from that angle. **Operational consequence: getting reliable bilateral ELBOW/KNEE coverage requires a second capture from the opposite side (camera moved, or subject turned), not a single-camera capture protocol change.** This is a capture-protocol / future-hardware question, not a code fix.
- **`MIN_LANDMARK_VISIBILITY` catches "the model doesn't know where this is," not "the model is confident about a wrong position" — a materially different, unsolved failure mode.** Confirmed against a live capture (a trunk-bend test), not just reasoned about: `leftShoulder/leftHip/leftKnee` gave a trunk angle of 112.7° while `rightShoulder/rightHip/rightKnee` on the *same physical bend* gave 159.6° — a 47° left/right disagreement — with every one of those six landmarks reporting visibility comfortably above the 0.5 threshold (knees 0.76/0.84, shoulders/hips near 1.0). The gate correctly let all of them through, because visibility measures MediaPipe's confidence in its own placement, not whether that placement is anatomically plausible. Not a code change — the gate is doing exactly what it was built to do; a plausibility check (e.g. cross-validating left vs. right, or against expected human proportions) would be a different, harder mechanism, not a threshold adjustment.

## Known gotchas
`PlatformUser` has two hand-added Postgres constructs Prisma can't see or manage: an FK to `auth.users.id` (`ON DELETE CASCADE`) and a `CHECK` constraint enforcing `companyId` nullability by role. `ManualInput` has a similar hand-added `CHECK` (`ManualInput_value_shape_check`) enforcing its value-shape by `inputType`. `MethodologyVersion` has a hand-added partial unique index (`MethodologyVersion_isActive_unique_when_true`, on `isActive` `WHERE "isActive" = true`) — Prisma's schema language has no filtered/partial index support. Because of these, `prisma migrate dev`/`migrate diff` don't work reliably against this schema (shadow-DB can't see `auth`; introspection won't diff a schema with an undeclared cross-schema FK) — migrations touching these tables are hand-written and applied via `prisma migrate deploy`, with hand-added constructs manually re-verified against the live DB afterward. Comments in the migration SQL mark exactly what to check. **General rule, not just these cases:** a brand-new enum value can never be referenced (in a `CHECK`, a seed `INSERT`, etc.) in the same migration that adds it — Postgres requires the enum-addition migration to be applied first, separately.

RLS is enabled (no policies) on all 24 tables (13 from the original assessment chain + the 11 process/risk/action tables added in M2, see below), which currently works because the DB role in `DATABASE_URL`/`DIRECT_URL` *owns* every table (it ran the migrations that created them) — table owners bypass RLS in Postgres regardless of RLS being "enabled." If the app's runtime connection is ever split to a narrower, non-owning role (a reasonable future hardening step), RLS will start being enforced for real, and with zero policies defined today every query would be denied. Add explicit policies before making that change.

**A fully-designed results dashboard is a planned future phase, not part of this build.** Keep `POST /api/posture-samples`'s response shape (`src/lib/capture/types.ts`) and the underlying data model presentation-agnostic — a future dashboard is expected to be a new consumer of the same routes and tables, not a rework of them. Don't reshape the response around any one UI's needs.

Scoring lookup built: `src/lib/scoring/lookup.ts` — `matchScoringRule` (pure per-row range check) and `lookupScoringRule` (fetches by bodyRegion+methodologyVersion, delegates to the pure matcher; `null` on no match, throws on an ambiguous/overlapping rule set).

Pose angle computation built: `src/lib/pose/angles.ts` — `computeBodyAngles(landmarks, cameraAngle)` takes a raw 33-point MediaPipe result and returns a `BodyAngleReading` per region (`{ ok: true, degrees }`, `{ ok: false, reason: "WRONG_CAMERA_ANGLE", ... }`, or `{ ok: false, reason: "INSUFFICIENT_VISIBILITY", failedLandmarks }` — never a thrown error for any of these routine/foreseeable conditions) for the 8 regions above. See "Known limitations" for the SAGITTAL gating and the SHOULDER/ELBOW camera-angle decisions.

Landmark-visibility gate, same principle as the camera-angle gate: each region's formula lists exactly which named landmarks it reads (`requiredLandmarksFor` inside `computeBodyAngles`), and if *any* of them has MediaPipe visibility below `MIN_LANDMARK_VISIBILITY` (0.5, a named constant, not empirically tuned yet), the whole region rejects with `INSUFFICIENT_VISIBILITY` naming every landmark that failed — no partial/best-effort reading off whichever landmarks did pass. Built after a real capture produced a confident-looking but meaningless `HIGH` NECK score: the hips were physically out of frame (landmark y-coordinate outside [0,1], visibility ~0.01-0.03), but nothing checked visibility before feeding that extrapolated position into the trunk vector both the magnitude and the sign depend on.

Capture-to-persistence pipeline built, end to end:
